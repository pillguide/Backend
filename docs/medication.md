# 복약과 알림 동작 — PR #12

## 확정된 API 정책

날짜와 시각은 `Asia/Seoul` 기준이다. 기존 경로, 요청·응답 DTO 필드, 회원별 소유권 검사를 유지한다.

| 항목 | 동작 |
|---|---|
| 홈 `nextDose` | 오늘 미완료 회차 중 현재 시각 이상인 가장 가까운 회차. 푸시 설정과 무관하며, 없으면 `null`. 같은 시각이면 기록 ID 순이다. |
| 체크리스트·통계 | 푸시를 꺼도 유지한다. 지난 시각의 미복용 회차도 체크리스트에 남는다. |
| 완료·취소 | 오늘 회차만 허용한다. 어제·내일 요청은 400, 다른 회원 회차는 404. 오늘 예정 시각 전의 완료는 허용하며 중복 완료는 최초 완료 시각을 보존한다. |
| 편집·삭제 | 지난 회차와 완료 회차의 약명·용량·시각을 보존한다. 미래 미완료 회차는 변경된 설정으로 재생성한다. 지난 일회성 회차를 수정해도 오늘 새 회차를 만들지 않는다. |
| 취소 | 로그아웃·토큰 이전·푸시 끄기·계획 삭제·복약 완료가 먼저 커밋되면 대기 발송을 중단한다. 이미 시작된 외부 요청과 접수된 메시지는 취소를 보장하지 않는다. |
| 재시도 | 예정 시각부터 5분까지 포함한다. 23:58 회차는 다음 날 00:03까지 가능하지만 전날 회차의 완료·취소는 불가하다. |
| 재활성화 | 다시 켜기·완료 취소·유효 토큰 재등록 후 현재 조건과 재시도 시각을 재평가한다. 성공 접수 기록이 있으면 재발송하지 않는다. |

프론트 담당자는 `nextDose=null`과 과거 체크 400을 처리해야 한다. 프론트 수정은 이번 범위에 포함하지 않았다.

## 발송과 경쟁 처리

준비 단계는 회차 ID만 전달한다. 실제 발송은 회원 잠금을 얻은 뒤 회차·계획·토큰을 다시 읽는다. 동일 회원의 토큰 변경, 로그아웃, 복약 변경도 같은 잠금을 사용한다. 토큰 이전은 두 회원을 ID 순으로 잠그고 소유권을 다시 확인한다. 경쟁 중 소유자가 바뀌거나 유일성 제약에 걸리면 409를 반환하므로 클라이언트는 토큰 등록을 다시 요청할 수 있다.

`notificationAttemptedAt`은 시도일 뿐 성공 증거가 아니다. `notificationAcceptedAt`은 FCM 접수 성공, `notificationRetryAfter`는 다음 시도 가능 시각, `notificationStoppedAt`은 영구 실패 중단을 나타낸다. 내부 상태는 API DTO에 추가하지 않는다. UNREGISTERED 응답이면 현재 토큰을 해제하고 새 토큰 등록을 허용한다. 401은 인증 갱신을 요청하고, 408·429·5xx 및 통신 실패는 재시도한다. 다른 영구 오류는 해당 회차를 중단한다.

Firebase Admin 9.4.3의 메시지 전송은 내부 재시도와 긴 대기를 포함하므로, 메시지 전송만 FCM HTTP v1 단일 요청으로 처리한다. 서비스 계정 인증 파일과 기존 Firebase 설정을 유지하며 payload의 제목·본문·`type`·`doseId`도 유지한다. 연결 제한은 2초, 응답 본문을 포함한 대기는 5초다. 인증 토큰 갱신은 회원 잠금·DB 트랜잭션 밖에서 수행한다. 이 5초 제한은 인증 갱신이나 전체 회원 순회 시간의 보장값이 아니다. 인증 서버 장애는 회차를 소비하지 않으며 다음 주기에 다시 준비한다.

429·서버 오류의 `Retry-After`는 초 또는 HTTP 날짜 형식을 해석하고 최소 60초를 기다린다. 통신 실패는 30초 뒤 재평가한다. 다음 시도가 5분 창을 넘으면 보내지 않는다. HTTP 타임아웃·응답 유실·성공 응답 뒤 DB 롤백은 이미 접수됐을 수 있으므로 사용자 결정대로 재시도하며 **중복 도착 가능성이 남는다**. Future 취소를 외부 접수 취소로 간주하지 않는다.

회원 잠금 때문에 같은 회원의 로그아웃·수정이 전송 응답을 기다릴 수 있다. 발송 트랜잭션 제한은 10초다. 토큰과 약 이름, 인증 키, 외부 오류 본문을 로그에 남기지 않는다. 프로필 갱신은 변경 컬럼만 갱신해 오래된 회원 객체가 해제된 토큰을 복구하지 않게 한다.

## 기존 DB 전환과 롤백

[전환 SQL](sql/pr12-notification-state.sql)은 기존 PR #12 `medication_dose` 테이블에 nullable 시각 컬럼 3개만 추가한다. 기존 행을 삭제하거나 성공으로 추정하는 보정은 하지 않는다. `notificationAttemptedAt`만 있는 기존 행은 결과 불명확으로 처리하며, 유효 창 안에서만 재시도할 수 있다. SQL은 반복 적용할 수 있고 PostgreSQL 기존 행 보존·재로딩 테스트로 검증한다.

운영 프로필의 기본값은 `ddl-auto=validate`다. 현재 저장소의 운영 매니페스트는 `update`로 덮어쓰지만 실제 배포 시 설정을 다시 확인해야 한다. `validate`로 운영할 때는 새 버전 시작 전에 기존 PR #12 스키마에 위 SQL을 단일 트랜잭션으로 적용한다. 예: 승인된 대상 연결에서 `psql --set ON_ERROR_STOP=1 --single-transaction --file docs/sql/pr12-notification-state.sql`. 이 파일은 복약 테이블 전체를 생성하는 최초 설치 스크립트가 아니다.

구버전으로 되돌릴 때 추가 nullable 컬럼은 남겨도 기존 매핑과 호환된다. 다만 구버전은 시도 기록만으로 재발송을 차단하므로 새 재시도·취소 정책을 보장하지 못한다. 구버전과 신버전 스케줄러를 동시에 운영하지 않는다. 운영 DB 적용, 매니페스트 변경과 배포는 이번 구현에서 실행하지 않았다.

## 검증 실행

Java 21로 `./gradlew check bootJar`를 실행한다. 일반 테스트는 H2, 고정 Clock, 모의 발송기와 로컬 HTTP 서버를 사용한다. `fcm.enabled=false`는 외부 인증이 필요 없는 기본 테스트 설정이며, 별도 설정 테스트는 임시 생성 키로 활성화된 Firebase 빈 구성도 검사한다. 실제 Firebase API나 실기기에는 접속하지 않는다.

격리 PostgreSQL 17 DB를 준비하고 `PG_TEST_URL`을 설정한 뒤 `./gradlew postgresTest`를 실행한다. 기본 테스트 계정은 `pillguide_test`이며 `PG_TEST_USER`·`PG_TEST_PASSWORD`로 변경할 수 있다. **이 테스트는 스키마를 생성·삭제하므로 개발·운영 DB를 사용하지 않는다.** URL이 없으면 작업이 실패하며 조용히 건너뛰지 않는다. 두 CI 워크플로 모두 독립 PostgreSQL 서비스를 띄워 이미지 빌드 전에 이 작업을 필수 실행한다.

검증 범위는 API 인증·응답·오류, 날짜 경계, 일정 이력, 재시도·취소, PostgreSQL 중복 발송 경쟁·토큰 이전·잠금 해제·프로필 갱신, 기존 스키마 전환, 로컬 HTTP payload·지연·오류 분류다. 실기기 수신, 운영 자격 증명 공급, 프론트 FCM 연결은 후속 작업이다.
